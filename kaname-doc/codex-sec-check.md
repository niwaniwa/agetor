  

  • Overall Verdict — 追加の隔離がある場合にのみ妥当（Reasonable only with additional isolation）

  提示された脅威モデルでは、Agetor を普段の開発アカウント・認証情報と同じ環境で動かすことは推奨できません。

  主な理由は次のとおりです。

  - worktree はファイル配置の分離であり、セキュリティ上の隔離ではありません。Codex では worktree 利用を理由にサンドボックスを解除する経路があります。
  - エージェント起動前の設定処理で、リポジトリ内のシンボリックリンクから認証情報を worktree 内へコピーさせられます。
  - .git まで攻撃者が支配する既存チェックアウトでは、Git の補助プログラム・hook を通じ、エージェントがプロジェクトコマンドを実行する前にコード実行できます。
  - API トークンを取得すると、タスク単位の制約なしにホストのターミナル、他タスク、接続済み Git アカウントを操作できます。

  一方、通常版の localhost API に、悪意ある Web サイトがトークンなしで侵入する完全な経路は確認できませんでした。

  調査はローカルファイルの読み取り・文字列検索だけです。リポジトリコード、テスト、インストーラーの実行、外部通信、ファイル変更はしていません。以下の「確認」は静的
  なデータフローの確認を意味し、実機での攻撃成功を意味しません。

  Confirmed Attack Paths — 確認した攻撃経路

  F-01 — 悪意ある Git メタデータによる、エージェント実行前のコード実行

  重要度：High／攻撃者 A

  - 場所・関数： src/bun/worktree.ts:36 git()、同ファイル hasUncommittedChanges()（100）、prepareWorkdir()（777）、getTaskDiff()（936）。
  - 攻撃者入力： 既存チェックアウトの .git/config、実行可能 hook、Git の外部補助プログラム設定。
  - 前提： 攻撃者が .git を含むローカルリポジトリを用意でき、Git がその所有者・設定を受け入れること。被害者が worktree 作成、状態表示、差分表示などを行うこと。

  攻撃チェーン

  攻撃者が用意した .git/config / hooks
  → prepareWorkdir()
  → git worktree add / git checkout
  → post-checkout hook
  → Agetor と同じユーザー権限でコード実行

  別経路として、hasUncommittedChanges() の git status --porcelain は core.fsmonitor、getTaskDiff() の git diff は設定済み textconv 等の影響を受けます。

  影響： ホストファイルの読み書き、取得可能な鍵・トークンの窃取、他リポジトリの改変、ユーザー権限での永続化。

  既存防御と限界： argv 配列は shell injection を防ぎますが、Git 自身の hook／設定に基づく実行を防ぎません。呼び出し側には hook・fsmonitor・textconv 等を無効化す
  る措置がありません。

  反証結果： 通常の remote clone では、相手の .git/config や .git/hooks はそのまま転送されません。したがって「公開リポジトリを普通に clone しただけで、この経路が
  成立する」とは評価しません。Agetor 自身による clone 実装も確認できませんでした。

  修正： 未信頼 Git の解析・checkout も隔離環境内で行う。ホスト上に残す読み取り処理では hook、fsmonitor、textconv、外部 diff を無効化し、許可する transport と設定
  を制限する。

  確信度：高。 成立条件は攻撃者によるローカル Git メタデータ支配です。

  F-02 — リポジトリ信頼確認を Agetor が自動で肯定する

  重要度：High／攻撃者 A、B

  - 場所・関数： src/bun/claude-tmux.ts:5039 STARTUP_CONSENT_DIALOGS、matchStartupConsentDialog()（5082）、confirmStartupDialog()（5127）、boot poller（6926）。
  - 関連箇所： src/bun/agents.ts:638 Gemini の --skip-trust。
  - 攻撃者入力： .claude 設定、hook、エージェント向け指示、タスク本文。
  - 前提： 被害者がそのリポジトリに Claude タスクを開始し、認識対象の信頼確認が表示されること。

  攻撃チェーン

  未信頼リポジトリ
  → Claude が「このフォルダを信頼するか」を確認
  → Agetor が肯定選択肢を検出
  → tmux send-keys で選択・Enter
  → リポジトリがユーザーの個別判断なしで trusted 扱いになる

  hook-installer.ts は古い Agetor 用設定だけを除去し、その他の hook／設定を維持します。

  影響： エージェント製品が設けた repository trust の判断が失われます。信頼済みプロジェクトの hook 等を実行する製品構成では、モデルがプロジェクトコマンドを選ぶ前
  の実行につながります。

  既存防御と限界： マーカーと肯定選択肢の照合は、誤ったダイアログへの入力を減らします。しかし、リポジトリを信頼してよい根拠にはなりません。未知のダイアログをユー
  ザーへ提示する処理はあります。

  修正： trust 確認を自動承認しない。リポジトリ設定・hook・MCP の許可を独立した信頼判断にする。隔離実行でもホスト資格情報を渡さない。

  確信度：自動承認は高。 具体的な hook の起動タイミングは外部 CLI の版・設定に依存し、このリポジトリだけから無条件の RCE とは断定しません。
  
  F-03 — 設定ファイルの symlink から、認証情報を worktree 内へコピーできる

  重要度：High／攻撃者 A

  - 場所・関数： src/bun/hook-installer.ts:146 applyAgetorSettings()、同ファイル writeJsonAtomic()（264）。
  - 呼び出し元： src/bun/claude-tmux.ts:6624 spawnClaudeViaTmux()。
  - 秘密の保存先： src/bun/core-creds.ts:40、src/bun/github-tokens.ts:28。
  - 攻撃者入力： commit された .claude/settings.local.json の symlink。
  - 前提： symlink が保持される環境で Claude タスクを開始すること。対象の JSON 資格情報ファイルが存在すること。

  具体的なデータフロー

  Agetor の配置は次です。

  <dataDir>/worktrees/<taskId>/.claude/settings.local.json

  ここに攻撃者が次のリンクを commit しておけます。

  settings.local.json → ../../../agetor-core.json

  すると、

  リポジトリ内 symlink
  → readFile(settingsFile) が <dataDir>/agetor-core.json を読む
  → JSON の token / port 等が settings オブジェクトに残る
  → worktree 内の一時ファイルへ書き込む
  → rename が symlink を通常ファイルで置き換える
  → 管理トークンのコピーが worktree 内に現れる

  リンク先を ../../../github-tokens.json にすれば、存在する場合は保存済み Git ホストトークンが同様にコピーされます。ユーザー名を推測する必要はありません。

  影響： ホスト側の秘密が、未信頼プロジェクトの通常ファイルに変換されます。その後のエージェント読み取り、添付・提出などで漏えいし得ます。管理トークンの利用は F-04
  へ接続します。コピー自体はエージェントのプロジェクトコマンド実行前に発生します。

  既存防御と限界：

  - 元の資格情報ファイルの 0600 は、同じ UID の Agetor による読み取りを防ぎません。
  - atomic rename は部分書き込みを防ぎますが、先行するリンク先の読み取りを防ぎません。
  - cwd の文字列上の owned 判定は、その内部の symlink を検証しません。
  - コピー先には秘密ファイル相当の mode 指定もありません。

  親ディレクトリ .claude 自体を外部へリンクした場合も、設定書き込みが worktree 外へ到達します。ただし、この経路の書き込み内容は設定 JSON であり、任意バイトの任意
  ファイル上書きとまでは評価しません。

  修正： 未信頼設定の最終要素・親要素の symlink を拒否する。競合を考慮した descriptor 基準のアクセスを使う。可能なら設定はリポジトリ外の専用領域に生成し、リポジト
  リ設定を無差別に取り込まない。

  確信度：高。

  F-04 — 侵害された一タスクから、ホスト・全タスク・接続アカウントへ横展開できる

  重要度：High／攻撃者 C

  - 起動・権限： src/bun/agents.ts:750 buildCommand()、src/bun/worktree.ts:361 gitWritableRoots()。
  - 環境継承： src/bun/fx-acp.ts:2403 spawnFxViaAcp()、src/bun/codex-tmux.ts:465。
  - 認可： src/bun/server.ts:350 isAuthorized()／authed()。
  - ホスト shell： src/bun/server.ts:5361、src/bun/terminals.ts:178、WebSocket handler（server.ts:574、5542）。

  前提： エージェントが悪意ある状態になり、実行モードまたはプロセス権限上、Agetor の資格情報ファイルを読めて loopback に接続できること。通常の非隔離実行ではこの条
  件を満たします。

  攻撃チェー

  侵害されたエージェント
  → 同じユーザーの agetor-core.json を読む
  → 全体共通 bearer token を取得
  → 別 task の取得・作成・変更
  → POST /tasks/:id/terminals
  → WebSocket に shell 入力
  → Agetor 権限でホストコマンド実行

  これは別の coding agent を起動せずに成立する経路です。

  さらに、同じトークンで harness、saved prompts、他タスクの入力、GitHub の操作 API に到達します。例えば src/bun/server.ts:1963 の PR merge は共通 token とリクエス
  ト値を検証しますが、タスク別の資格情報・権限確認はありません。

  影響：

  - 他 worktree・他リポジトリの改変。
  - harness の bin/env や saved prompts を用いた将来タスクの汚染。
  - 接続されたトークンの権限内で GitHub 等の操作。
  - ホスト上のユーザー所有ファイルへのアクセスと永続化。

  既存防御と限界：

  - Claude へ API_TOKEN を明示注入する古い処理は削除されています。しかし同じ UID で token ファイルを読めます。
  - 別 HOME／CODEX_HOME は資格情報の選択であり、filesystem namespace の隔離ではありません。
  - Codex auto は外部 Git dir があると danger-full-access と approval_policy=never になります。通常の linked worktree がこの条件です。
  - Cursor auto は --force --sandbox disabled。
  - tmux は通常、既存の default socket を使います。専用名を使っても同一 UID に対する強い境界にはなりません。

  修正： エージェントを別の OS セキュリティ境界へ移し、ホスト管理 token・ホーム・共有 socket を渡さない。API は task ごとの capability と操作別認可に分割する。

  確信度：高。 外部から別途強制された sandbox が読取り・通信を拒否する場合、この経路はそこで止まります。それは Agetor の保護ではありません。

  F-05 — 開発版の UI サーバー乗っ取りで、別ユーザーが管理トークンを取得できる

  重要度：High／攻撃者 E、開発版限定

  - 場所・関数： src/bun/index.ts:99 getMainViewUrl()、boot token 注入（534）、BrowserWindow 構築（559）。
  - 攻撃者入力： http://localhost:5173 の HTTP 応答と HTML。
  - 前提： Agetor の channel が dev。正規 Vite サーバーがポートを占有しておらず、攻撃者が先に listen できること。

  攻撃チェーン

  別ユーザーのローカルプロセスが 5173 を確保
  → Agetor の HEAD に応答
  → getMainViewUrl() が攻撃者サーバーを採用
  → URL fragment／window.__AGETOR に管理トークンを注入
  → 攻撃者 JavaScript が token を読む
  → F-04 のターミナル API
  → 被害者ユーザー権限でコード実行

  HEAD の成功ステータスやサーバー固有の秘密も確認していません。

  既存防御と限界： API のランダム token と資格情報ファイルの 0600 は、この経路では役立ちません。Agetor 自身が token を攻撃者ページに渡します。localhost:5173 は
  CORS 許可対象です。

  修正： 応答があるだけで UI を採用しない。Agetor が起動・所有する開発サーバーとの認証済み handoff に限定する。外部ページへ全体管理 token を渡さない。

  確信度：高。 stable 版では bundled view を選ぶため、この経路は成立しません。通常の Web サイトだけではローカル listen はできません。

  F-06 — CLI 配布物の差し替えを、同一配布元の checksum だけでは検出できない

  重要度：High／攻撃者 F

  - 場所： scripts/install.sh:31 download/checksum、49–52 の実行属性・quarantine 処理、72 の実行。
  - 攻撃者入力： GitHub release の CLI artifact と .sha256。
  - 前提： 攻撃者が release artifact を変更でき、被害者が installer を使うこと。installer 自体を変更できなくても成立します。

  攻撃チェーン

  CLI binary と checksum を同時に差し替える
  → SHA-256 一致
  → chmod +x、quarantine 削除
  → 配置
  → installer が --version で実行
  → 被害者ユーザー権限でコード実行

  既存防御と限界： HTTPS と必須 checksum は通信改ざん・破損を抑えます。しかし期待値も同じ侵害可能な配布元から取得します。installer は既知の署名者に対する署名検証
  を行いません。

  ビルド側の codesign／notarization は存在しますが、installer がその署名者を強制する処理とは別です。

  修正： installer 内で固定した信頼根による artifact／manifest 検証を必須化する。署名者 identity を検証し、検証前に実行・quarantine 除去しない。

  確信度：高。

  Maximum Blast Radius — 最大被害範囲

  Agetor 本体が侵害された場合

  Agetor の OS ユーザーが読める・書ける全領域が対象です。~/.agetor の DB、保存済み PAT、task 履歴、worktree、harness 設定を含みます。

  GitHub 認証は保存済み token に加えて、環境変数と gh auth token へフォールバックします（src/bun/github.ts:860）。接続アカウントへの影響は、その token の scope と
  サーバー側権限までです。

  SSH 秘密鍵のファイル、git credential store、Codex の auth.json、Claude alias の資格情報ファイルも、読取り権限があれば対象です。暗号化された秘密鍵の復号やハード
  ウェア鍵の抽出まで保証されるわけではありません。SSH agent socket が利用可能なら、秘密鍵の抽出なしでも署名・認証に使われ得ます。

  macOS Keychain には独立した ACL／承認があります。Agetor の資格情報取得実装にも拒否・タイムアウト処理があり、Keychain の全秘密を無条件取得できるとは評価しませ
  ん。

  永続化先は、書き込み可能な shell 起動設定、ユーザーサービス、Git hook、agent 設定、harness、saved prompts などです。

  一つの coding agent が侵害された場合

  非隔離構成では上記に近い範囲です。Agetor 管理 token の取得後は、agent 自身に渡されなかった他 harness の設定や Git 操作も利用できます。

  製品の OS sandbox が強制される場合は、その制限が残ります。ただし Agetor の ask 表示や permission UI 自体は、侵害されたプロセスを隔離するものではありません。

  一つの repository が悪意ある場合

  - .git も支配：F-01 からユーザー権限での実行。
  - 通常の tracked content のみ：F-03 の秘密コピー、F-02 の trust 自動承認が問題。
  - 本文・指示だけ：モデルを悪意化させる成功率は、この静的解析では確定できない。成功した場合は F-04 の範囲へ拡大。

Rejected Attack Hypotheses — 棄却・未成立の仮説

  - Issue title の $()、引用符、改行 → tmux shell injection
    Claude は argv、Codex は stdin 用ファイル、Cursor は引用済み展開です。本文を shell ソースとして再解釈する経路は確認できません。

  - Issue 内容を無条件で trusted instruction として渡す
    src/shared/issue-task.ts:21 に明示的な untrusted-content 注意文があります。これは意味上の防御であり OS 境界ではありませんが、存在を無視して「防御なし」とは評
    価しません。

  - CSRF／DNS rebinding だけで task 作成・起動
    src/bun/api-config.ts は既定で32バイトの乱数を生成します。cookie 認証ではなく、HTTP／WebSocket とも token が必要です。DNS rebinding は token を生成しません。
    未認証 /health は識別情報のみです。

  - 不許可 Origin が CORS で完全拒否される
    これは逆に成立しない防御仮説です。実装は不許可時に Access-Control-Allow-Origin: null を返します。ただし token は引き続き必要なので、これだけを RCE として報告
    していません。

  - 悪意ある SVG → 同一 origin script → token 窃取
    preview／diff blob には nosniff と Content-Security-Policy: sandbox; default-src 'none' があります。この経路は確認できません。

  - Issue 中の画像参照 → ローカルファイルの自動表示
    MdImage の Issue／PR 用 scope は allowLocal: false です。agent 出力用 scope と区別されています。

  - @file の symlink で参照範囲を脱出
    src/bun/project-files.ts:445 に realpath containment 検証があります。この防御は F-03 の設定読み込みには適用されません。

  - agetor:// URL から直接 shell 実行
    src/bun/deep-link.ts は task を開く用途に限定されています。通常の外部リンクも HTTP／HTTPS／mailto に制限されています。

  - orphan worktree の ../ → 任意ディレクトリ削除
    resolveWorktreeDir() は区切り文字、..、不整合な basename を拒否します。単純な symlink を再帰削除しただけで、そのリンク先まで削除されるとも評価していません。

  - 別 UID が agetor-core.json／PAT store を普通に読む
    両ファイルは 0600 で保存します。ただし dataDir は 0700 を強制せず、DB・prompt・log 全体にも秘密向け permission の強制はありません。別 UID への露出は親ディレク
    トリ権限・umask・格納内容に依存します。F-05 はこのファイル防御を経由せず成立します。
