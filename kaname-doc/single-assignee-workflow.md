# 単一担当の開発ワークフロー

更新日: 2026-10-03

状態: ソース実装・分離環境での検証済み。稼働版へのビルド・再起動・データ移行は未実施。

## 今回の仕様

一件の依頼を同じ CLI・モデル・effort で調査、要件整理、実装、検証、自己レビューまで進め、PR を人が承認した後に Squash マージする。GitHub で実際にマージされたことを確認して Done とする。親 Issue に一つの専用 branch／worktree と一つの PR を対応させる。

Issue は既存の通常 Task／Pipeline と別の永続データとして扱う。Backlog 保存だけでは起動せず、Ready を調査・実装・検証・commit・push・PR 作成の実行許可とする。マージには PR の head SHA に対応する別の承認が必要。追加変更で承認は失効する。稼働版へのデプロイは自動化しない。

依頼の必須入力はプロジェクトと実現したいこと。調査で要件案・合格条件・前提を保存し、重要な未決事項だけ質問する。回答待ちでは CLI を終了して枠を解放し、回答後は保存済みの要件・成果・回答から新しい実行として再開する。旧版への回答や依頼の単なるクローズを承認・再開として扱わない。

プロジェクトには Git remote・基準ブランチ、担当設定、検証コマンドを設定する。GitHub の対象 repo は明示した remote URL から解決して固定する。未設定の検証コマンドは調査後に設定を求める。差分ゼロや解決できない競合は人の対応待ちとし、空 PR や自動 Done を作らない。

## 第15節から今回確定した変更

- 通知は **画面内の「あなたの対応待ち」と通知履歴のみ**。ブラウザーを閉じても記録を保持する。外部通知先の接続・送信は後続段階。
- 日次上限は **新ワークフローだけ**を全プロジェクトで合算する。既存の通常 Task／Pipeline と KANAME 外の CLI 利用は対象外。
- 一件の中の担当は一人とし、CLI 内部の追加委譲も無効化する。別担当へのレビュー委譲・並列分担は後続段階。
- マージ方式の初期値は Squash。

## 利用時間と復旧

初期値は親 Issue ごと2 Agent 時間、日次6 Agent 時間、UTC。一回の CLI は停止猶予を含め三十分。全体で二件、プロジェクトごと一件を同時進行し、CLI の実行枠は最大三つ、自動修正・再試行は工程ごと二回までとする。80%消費時に一度通知し、上限で止める。上限到達後は日付変更だけでは再開せず、明示的な再開が必要。

実行前に時間を予約し、実行終了を確認して精算する。調査・実装・自己レビュー・再試行と、CLI 実行中のツール／通信待ちを含める。キュー・人の回答・CI 待ちは含めない。取得できない金額・トークン・契約残量を推定で補わない。

日付をまたぐ実行は、タイムゾーンに従って日別の時間を一括予約する。翌日分も確保できれば継続し、翌日分が不足すれば停止猶予を含めて日付境界までに停止する。実消費は開始・終了区間から日別に精算する。終了不明の場合は全日分の予約を維持し、新規起動を止める。

新ワークフローの実行は、一回につき systemd user service と管理 DB を開かない Bun worker を使う。非対話 CLI のログ・結果を保存し、管理サービス再起動後に取り込む。CLI 起動前に絶対期限の停止タイマーを設定し、管理サービスが停止中でも予約期限を守る。unit と子プロセスの終了を確認できない間は予約を解放しない。

この仕組みは信頼済みリポジトリを同一 OS ユーザーで扱う運用上の制御であり、Agent と管理サービスの資格情報を隔離するセキュリティ境界ではない。

## 画面から使う手順

1. ヘッダーの「開発ワークフロー」を開く。通常 Task と既存 Pipeline は別画面のまま利用できる。
2. 「設定」で対象プロジェクト、remote、基準ブランチ、担当 CLI、モデル、effort、検証コマンドを保存する。モデルは必須、Codex の effort も必須。保存済みプロファイルから担当情報を入力できる。検証コマンドは専用 worktree を作業ディレクトリとして一行ずつ実行されるため、その worktree 内の依存関係の準備も必要に応じて含める。
3. GitHub の接続を確認し、そのプロジェクトの「GitHub への push・PR 作成を有効にする」を ON にする。初期値は OFF。CLI ログインと Git／GitHub 認証はサービスを動かす OS ユーザーの既存設定を使う。
4. プロジェクトと「実現したいこと」を入力し、Backlog に保存する。内容と設定を確認して「Ready にして開始」を押す。
5. 「あなたの対応待ち」に質問が出たら回答する。要件案、差分、実行ログ、検証・履歴を確認できる。ブラウザーを閉じても処理・対応待ち・通知履歴は保持される。
6. PR の対象 SHA、差分、ローカル検証結果、CI を確認する。チェックボックスを選び「承認して Squash マージ」で、その SHA だけを承認する。修正が必要なら差し戻す。CI が未設定の repo は「未報告」と表示し、実行済みのローカル検証を確認する。
7. 停止後は理由を解消して明示的に再開する。上限を増やすだけでは自動再開しない。「指示を追加して再開」は新しい要件版を調査する。取消済みの依頼は再開しない。

開始済みの担当・接続先は固定する。実装以降の質問への回答は要件を再調査して版を更新し、検証・承認をやり直す。停止中に検証コマンドを変えて再開した場合も、検証・自己レビュー・SHA 承認をやり直す。通常の GitHub マージボタンや自動マージ設定から新ワークフローの承認を迂回する操作は拒否する。

push・PR 作成・マージの外部書き込みが実行中の場合、停止・取消は結果が確認できるまで受け付けない。まだ開始していない処理は停止できる。CLI の手動停止は、別の依頼の Git 処理の完了を待たずに発行する。

## 実行環境と保存先

Linux、Bun、稼働する systemd user manager が必要。KANAME 管理サービスと worker を同一ユーザーで動かし、そのユーザーから `systemd-run --user`／`systemctl --user` が利用できることを前提とする。SSH 切断後も user manager を維持する運用は既存のサービス設定に合わせる。

今回検証したバージョンは Bun 1.3.13、systemd 259、Codex 0.159.0、Claude Code 2.1.285。新 runner は両 CLI の上記バージョンを明示的に許可している。CLI 更新後は勝手に互換とみなさず、委譲無効化・構造化結果・停止を再検証して許可リストを更新する。既存 Task の CLI バージョン方針とは別。

- SQLite migration `062_development_workflows` に Issue、要件版、質問・回答、実行、ジョブ、予約、利用時間、通知、重複防止キーを保存する。
- データディレクトリ内の `development-attempts/<attemptId>/` に manifest、イベント、結果、実コマンドの検証記録、終了記録を保存する。
- `development-git/<issueId>.json` に固定した remote・branch・PR の識別情報、`development-git/worktrees/<issueId>/` に専用 worktree を保持する。完了後の自動削除は行わない。
- Worker は `src/bun/workflow-worker.ts` を Bun で起動する。今回の対象はソース配置による headless 運用で、単一バイナリへの worker 同梱は未対応。

API は既存認証の内側の `/workflow/*` に追加した。Issue 作成・取得、revision と重複防止キー付き操作、質問回答、SHA 承認、設定、利用上限、対応待ち、通知、ログ・差分、SSE を提供する。ブラウザーは既存 gateway の同一 origin を使い、SSE は更新通知、再取得する DB の内容を確定状態として扱う。リンクを開くことや SSE の受信だけで承認しない。

稼働 checkout と異なる作業コピー、一時 DB・worktree・ポートを使用した。実 GitHub 書き込みと外部通知は行っていない。

障害系では、古い回答・承認、PR 応答消失、チェックのページネーション、SHA 変更、同一の GitHub 修正要求の重複、取消後の遅延結果、停止・再開中の非同期処理、終了不明時の予約保持、日またぎと夏時間、予約途中のロールバックを検証した。モデルの「検証成功」という申告だけでは先に進まず、worker が実行したコマンド・終了コードと検証対象 SHA が必要。

再現用コマンド（Bun が PATH にある環境）:

```sh
bun run typecheck
bun run test:kaname-workflow
bun run build:web
bun run test:kaname-workflow-browser
bun run test:kaname-workflow-runner
```

ブラウザー検証には Playwright の Chromium と OS ライブラリが必要。runner 検証には host の systemd user bus が必要。既定の runner 検証は偽 CLI で、実 CLI を使う場合だけ `bun scripts/kaname-workflow-runner-smoke.ts --real=codex --scenario=edit` のように明示する。Claude は `--real=claude-code --model=opus-5.5` を使用した。実 CLI はログイン済みアカウントの利用を消費する。

今回の一時検証記録: systemd `/tmp/kaname-workflow-smoke-bOgvTA`、Codex 編集・検証 `/tmp/kaname-workflow-smoke-pFSBe3`、Claude 編集・検証 `/tmp/kaname-workflow-smoke-D6sV6P`、最終ブラウザー確認 `/tmp/kaname-workflow-browser-fQr8RD`、既存 headless 復旧 `/tmp/kaname-smoke-PXYpLy`。一時ファイルのため永続保存は保証しない。

## 残課題と稼働版への反映

実 GitHub への push・PR 作成・レビュー・マージを含む end-to-end は、今回の書き込み禁止に従い未検証。GitHub API と一時 Git リポジトリのテストで確認した範囲と区別する。外部通知、複数担当、通常 Task／Pipeline を含めた利用上限、完了 worktree の整理、デプロイ自動化は後続。

今回行ったのはソース変更と検証まで。稼働版の `dist`、サービス、DB、Cloudflare 設定は変更していない。反映時は別作業として、実行中の通常 Task と新 workflow の worker がないことを確認し、データをバックアップして、Web build・サービス再起動・migration 適用後の認証と画面を確認する。稼働中の配信ディレクトリを直接ビルドで差し替えない。commit・push・PR 作成は未実施。
