# 完了時の追加タスク起票 — 初版仕様

記録日: 2026-09-30  
状態: 2026-09-30 にユーザーが仕様を了承。開発用コピーでの実装と実ブラウザー・両実 CLI の検証を経て、別途の反映指示に基づき 2026-10-02 に稼働版へ反映した。[実装・検証記録](done-followups-implementation.md) と [反映記録](done-followups-deployment.md) を参照。KANAME 自身で開発した最初の小さな機能として扱う。

## 目的と確定した操作

完了した作業から見つかった別件や改善案を、元タスクと関連付けて KANAME の Backlog に残す。起票後に人が内容と優先順位を確認し、既存 UI で明示的に Ready／開始操作をするまで実行しない。既存 Task の開始方式は変更しない。

この会話でユーザーが選択した二点:

1. CLI の成功で Review に入った時点では起票せず、**人が Done にした時に起票する**。
2. **タスクごとに ON にする。初期値は OFF**。生成されたタスクは常に Backlog に置き、自動実行しない。

以下は、この二点と既存の方針を具体化する初版の仕様である。元タスクを自動で Done にする機能ではない。今回の既存 Task を、計画上の完成版の親／子 Issue として扱わない。

## 対象と対象外

- Codex／Claude Code を利用する通常のタスクを対象にする。候補は同じ作業を担当した CLI が終了時にまとめ、候補作成だけの追加 CLI は自動起動しない。
- 独立して進められる改善・別件を対象とし、元依頼の必須条件の未達やテスト失敗を追加タスクに移して完了扱いにしない。この区別を CLI への指示に含め、成果の完了判断は引き続き人が行う。
- 起票先は KANAME 内の同じプロジェクト。GitHub Issue、PR、通知、累積時間制御、複数担当への自動分解は含めない。
- 初版では Pipeline の親・内部ステップ、他の CLI 種別は対象外。対象外タスクには設定を提供せず、API でも有効化を拒否する。
- 古い Done タスクを走査して後から起票する処理や、別の実行・別タスクをまたぐ意味的な類似判定は含めない。

## 利用の流れ

1. タスクの作成画面または詳細で「Done 時に追加タスクを起票」を ON にする。
2. 次の実行を開始する。サーバーはその実行に候補の出力指示を追加する。
3. CLI は通常の成果とともに、0〜5件の候補を所定の形式で返す。候補がなければ明示的に0件を返す。
4. 正常終了して Review に入る。詳細画面で候補の件数・内容を確認できる。この段階では Backlog タスクを作らない。
5. 人が Done にする。有効な候補から追加タスクを Backlog に作り、元タスクに作成結果とリンクを表示する。
6. 必要なら生成されたタスクの内容や設定を既存 UI で編集する。実行には人の Ready／開始操作が必要。

設定の変更は次の実行の候補収集から適用する。OFF だった実行に対して後から ON にしても、追加 CLI の起動や過去ログの推測で候補を補わない。Done 操作時にも ON であることを必須とし、Done 前に OFF にすれば起票を抑止できる。既に生成したタスクは、設定変更で削除しない。

生成されたタスクのこの設定は必ず OFF にする。必要なら人が次の実行前に ON にできる。

## 候補と生成タスクの内容

各候補は以下を持つ。

| 項目 | 内容 |
|---|---|
| タイトル | 何をするタスクか |
| 理由・根拠 | なぜ必要か、元作業で何が分かったか |
| 実施内容 | 対象範囲と実現したいこと |
| 合格条件 | 完了を確認できる条件を一つ以上 |

サーバーが付ける情報:

- 元タスク ID、元の実行 ID、候補を特定する ID、作成日時、生成したタスク ID。
- 元タスクと後続タスクの双方から辿れる関連。
- 同じプロジェクトと元タスクの基準作業ディレクトリ。一時的な `worktreePath` は引き継がない。
- 元タスクの CLI・モデル・権限モード・分離方式を初期設定として引き継ぐ。既存の worktree、作業ブランチ、PR、実行中セッション、Pipeline の紐付けは引き継がない。未開始の通常タスクとして既存の開始処理を使う。

生成タスクの本文には候補の理由・実施内容・合格条件と元タスクへの参照を入れる。Done はマージ済みを意味しないため、起票だけで元タスクの未統合の変更を取り込んだことにはしない。着手に元の成果が必要なら、その前提を本文に残して人が開始前に確認できるようにする。

CLI の出力から作業ディレクトリ、CLI 設定、起票先、Ready 状態などを自由に指定させない。候補は文字列データとして検証・保存し、出力中の命令や API 呼び出しを実行しない。

## 対象の実行と再実行

- Done 時点で元タスクが参照する最新の実行を対象として固定する。
- その実行が成功し、候補収集が有効で、処理・実行待ちキューの後続入力・背景処理が残っていない場合に限り起票する。未送信の下書きやメッセージの Backlog トレイは実行待ちに含めない。
- 最新の実行が失敗・キャンセル・実行中の場合、さらに前の成功した実行へ戻って起票しない。起票できない理由を表示する。
- Review 中に追加指示で新しい実行を始めた場合、旧候補を今回の候補として使わない。最新の実行の結果を待つ。
- 同じ実行の同じ候補は一度だけ起票する。Done と他の列を往復しても、新しいタスクを増やさない。
- 新しい実行から出た候補は別の起票対象になり得る。過去の関連タスクは画面に残すが、文章の意味による重複統合は初版では行わない。
- 生成済みタスクを人が編集・移動・削除しても、再処理で編集を上書きしたり削除したタスクを再作成したりしない。元の起票記録は保持する。

## 候補なし・失敗・復旧

| 状態 | 表示・処理 |
|---|---|
| 有効な候補が0件 | 「追加タスクなし」。起票成功と区別可能な正常な結果として保存 |
| 候補の出力がない・形式が不正 | 「候補を取得できませんでした」と理由を表示。0件と見なさず、推測でタスクを作らない |
| 起票成功 | 件数と作成したタスクへのリンクを表示 |
| 起票失敗 | 「追加タスクの起票に失敗」と理由・再試行操作を表示。有効な候補を保持 |

候補取得や起票の失敗だけで、元タスクの成果や Done を取り消さない。起票の失敗に対する再試行は保存済み候補の登録だけを行い、CLI を再実行しない。候補自体の修正が必要なら、人が既存の追加指示機能で新しい実行を開始する。

候補・対象実行・起票要求・結果を SQLite に保存する。Done の変更と起票要求の保存を同じトランザクションにし、追加タスクの一括作成と起票済み記録も原子的に保存する。HTTP の再送、二重クリック、二つの画面からの操作、起票途中のサービス再起動でも、同じ候補から作るタスクは一件だけにする。

サービス再起動後は、保存済みで未処理の起票要求を回収する。元タスクの削除・対象実行の変更・Done の取り消し・設定 OFF を作成直前に再確認し、古い要求は起票しない。競合で既に作成が完了していた場合は、その結果を表示し、生成タスクを巻き戻さない。既に失敗として記録した要求は無限に再試行せず、人の再試行を待つ。

## 合格条件

1. 既存タスクと新規タスクの初期値が OFF で、OFF の通常操作では候補生成指示や自動起票が加わらない。
2. ON にした Codex／Claude Code のタスクが正常終了すると Review に入り、候補だけが表示される。追加タスクや追加 CLI はまだ起動しない。
3. 人が Done にすると、候補と同じ件数の独立した Backlog タスクが作られ、両方向の関連と必要な本文・設定が保存される。
4. 候補0件は「追加タスクなし」、欠落・形式不正・件数上限超過は取得失敗として区別される。部分的な推測起票や黙った切り捨てをしない。
5. 生成タスクは未実行で、自動起票設定も OFF。Ready／開始操作までは CLI のプロセスも Run も作られない。
6. 最新の実行が失敗・キャンセル・実行中の場合や、Review から追加実行した場合に、古い成功結果から起票されない。
7. Done の再送・連打・列の往復・複数画面の操作でも、同一実行の同一候補から作るタスクは一件だけ。
8. 起票直前・保存途中・保存直後にサービスを停止しても、再起動後に重複や部分的な二重作成がなく、結果を確認できる。
9. 保存済み候補の起票が失敗した場合、元タスクの Done と候補を保ち、理由を表示する。明示再試行で復旧でき、追加 CLI は起動しない。
10. OFF への変更・対象実行の更新・Done の取り消しが先に成立した場合、古い未処理要求は起票しない。生成済みタスクの編集・削除後の再送も元に戻さない。
11. 元タスクが worktree を使用していても、後続タスクは消去され得る worktree のパスや元の実行セッションを引き継がない。
12. 作成するタスクの起票先や状態を、CLI の候補出力で変更できない。GitHub への書き込み・外部通知・Git 操作を起票処理から実行しない。
13. CLI の候補出力・正常終了直後にサービスを停止しても、保存されたログから候補を回収し、再起動後に Review で確認して Done 起票できる。
14. ON／OFF の変更を実行開始前・実行中・Review 中に行っても、候補収集の設定が既存の実行に遡って変わらない。Done 前の OFF は起票を抑止し、対象外の CLI／Pipeline では有効化できない。

## KANAME 自身で実装するときの条件

- この文書と `implementation-plan.md` 第15節を実装タスクから参照する。
- 稼働中の管理サービスと、開発・検証用のコード配置／データディレクトリ／ポート／tmux socket を分ける。候補生成の試験には専用タスクだけを使う。
- 最初にモックで成功・0件・不正出力・失敗・再送・再起動・競合を検証する。その後、両実 CLI を一時ディレクトリの小さなタスクで確認する。
- 型チェック、Web ビルド、変更箇所の関連テスト、実ブラウザーでの ON → Review → Done → Backlog の確認結果を記録する。
- commit・push・PR 作成・マージ・remote／履歴変更は行わない。外部通知・GitHub 書き込みの試験に実サービスを使わない。
- 実装開始は UI に登録したタスクへの明示的な開始操作による。稼働版への反映は今回の実装タスクに含めない。
