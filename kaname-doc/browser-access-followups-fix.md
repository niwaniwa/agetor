## 公開画面へのアクセス

従来の gateway は `Sec-Fetch-Site: cross-site` をすべて拒否しており、外部リンクや認証サービスからのリダイレクト後の画面表示も403になった。ユーザーは URL 末尾に `/` を付けるとアクセスできたと報告している。今回再現したのは外部遷移の拒否であり、末尾 `/` の有無そのものが原因だったとは断定しない。

`GET /` と `GET /index.html` のうち、`Sec-Fetch-Mode: navigate`、`Sec-Fetch-Dest: document` のトップ画面遷移だけを許可した。Host と明示された Origin の完全一致検証は維持する。API、認証 API、静的資産、iframe、更新操作、WebSocket に例外を適用しない。Cookie の属性も変更していない。

実 Chromium で別サイトからのリンク直遷移と302経由の遷移を再現し、画面が200で表示され、その後の同一サイト API が既存の Strict Cookie で認証されることを確認した。

## 追加タスクの候補表示

報告された元タスクの最新実行では、候補1件が正常に収集済みだった。問題は会話ログが内部プロトコルをそのまま Markdown に渡している点で、候補保存や起票の失敗ではなかった。

有効な出力を「追加タスクの提案」カードに変換し、タイトル、理由・根拠、実施内容、合格条件を表示する。元の回答は「元の出力を表示」に折りたたんで保持する。各項目は文字列として描画し、HTML を実行しない。

厳密な候補パーサーを副作用のない共有モジュールへ抽出し、バックエンドと表示側で共用する。既存の判定条件・エラー・起票処理は変更しない。プレビューは実行開始時の ON 設定と、読み込んだメインログの厳密な解析成功を条件とする。単一メッセージ末尾に完結するタグだけをカード化し、途中・不正・重複・引用・コード例・複数メッセージに分割されたタグは原文表示を維持する。

カードは出力のプレビューであり、保存・起票の確定状態は上部の「Follow-up tasks」で確認する。初期 OFF、人が Done にした時だけ Backlog に起票、自動実行なし、同一候補の重複防止という仕様を維持する。
